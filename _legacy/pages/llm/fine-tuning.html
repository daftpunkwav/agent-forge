微调：让通用模型成为专家

从预训练到领域专家——理解Fine-tuning的完整流程、策略选择和工程实践。

为什么需要微调？

预训练模型是"通才"——它知道很多，但对特定领域的理解不够深入。微调（Fine-tuning）是在预训练模型的基础上，使用领域特定的有标注数据继续训练，让模型成为该领域的"专家"。

核心洞察：微调不是"重新训练"，而是在预训练知识的"冰山"上，雕刻出你需要的形状。小数据 + 正确的方法，往往比大规模训练更有效。

微调方法

Full Fine-tuning

更新模型所有参数。效果最好，但成本最高。

  • 需要大量GPU资源
  • 适合有充足数据的大型任务
  • 风险：灾难性遗忘

LoRA / QLoRA

LoRA（Low-Rank Adaptation）：冻结原始权重，只训练低秩分解矩阵。QLoRA进一步用4-bit量化降低显存需求。

  • 单卡可微调7B-70B模型
  • 效果接近全量微调
  • 训练速度提升2-3倍
  • 当前主流方案

Prompt Tuning / P-Tuning

只优化输入的soft prompt（可学习的虚拟token），模型权重完全冻结。适合快速适配但效果较弱。

LoRA微调实战

Python · LoRA微调（使用unsloth） 
from unsloth import FastLanguageModel
from trl import SFTTrainer, SFTConfig

# 1. 加载模型（4-bit量化，QLoRA模式）
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/llama-3.1-8b-bnb-4bit",
    max_seq_length=2048,
    load_in_4bit=True,
)

# 2. 应用LoRA
model = FastLanguageModel.get_peft_model(
    model,
    r=16,                    # LoRA秩
    lora_alpha=16,           # LoRA缩放
    lora_dropout=0,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    use_gradient_checkpointing="unsloth",
)

# 3. 准备数据
from datasets import load_dataset
dataset = load_dataset("jsonl", data_files="agent_forge_training.jsonl")

# 4. 配置训练
trainer = SFTTrainer(
    model=model,
    train_dataset=dataset["train"],
    peft_config=model.peft_config,
    args=SFTConfig(
        output_dir="./lora-agent",
        per_device_train_batch_size=2,
        gradient_accumulation_steps=4,
        max_steps=200,
        learning_rate=2e-4,
        fp16=True,
        logging_steps=10,
        save_strategy="steps",
        save_steps=50,
    ),
)

# 5. 开始训练
trainer.train()

# 6. 保存
model.save_pretrained("./lora-agent-final")
tokenizer.save_pretrained("./lora-agent-final")

微调策略

数据准备

  • 质量 > 数量：1000条高质量数据 > 10万条嘈杂数据
  • 格式一致性：训练数据格式要与推理格式完全一致
  • 去重：训练集和验证集不能重叠
  • 覆盖边界case：包含困难样本和错误答案的纠正

训练参数

  • 学习率：LoRA通常用 1e-4 ~ 3e-4，全量微调用 1e-5 ~ 5e-5
  • Batch Size：受显存限制，通常1-4，用gradient accumulation放大
  • Epochs：3-5个epoch通常足够，过多会过拟合
  • LoRA rank：8-64之间，越大表达能力越强但越慢

评估与迭代

  • Hold-out验证集：从未参与训练的独立数据
  • LLM-as-Judge：用更强的模型评估微调后模型的输出质量
  • A/B测试：对比微调前后在真实任务上的表现
  • 持续迭代：分析bad case → 补充数据 → 再训练

微调 vs 其他方法

  • vs RAG：微调改变模型"知道什么"，RAG改变模型"能查到什么"
  • vs Prompt Engineering：微调更持久但成本更高；Prompt更灵活但有上限
  • vs 纯API调用：微调适合需要特定格式/风格/知识的场景
  • 组合使用：RAG + 微调 + 好的Prompt = 最强方案

最佳实践

  • 先用Prompt Engineering：如果Prompt能解决问题，就不需要微调
  • 数据质量第一：宁可100条精品，不要1万条垃圾
  • 从LoRA开始：先验证效果再考虑全量微调
  • 监控过拟合：验证集loss如果持续上升就停止
  • 版本管理：每个微调版本记录数据版本、参数、效果指标
