上下文管理

Context 是 Agent 的"工作记忆"。如何设计、管理和优化上下文，直接决定了 Agent 的能力上限和运行成本。

什么是 Context Window？

LLM 有一个固定的"上下文窗口"（Context Window）——模型一次能"看到"的文本长度。GPT-4 是 128K tokens，Claude 3 是 200K tokens。超出这个窗口的内容，模型就"看不见"了。

对于 Agent 应用，Context Window 就像一张有限大小的桌子——所有相关的信息（对话历史、工具结果、系统指令）都要放在这张桌子上。放不下怎么办？这就是上下文管理的核心挑战。

核心洞察：不是所有信息都有同等价值。上下文管理的本质是：在有限的窗口内，始终保留最关键的信息。

Context 的组成

一个完整的 Agent Context 通常包含以下部分：

  • System Prompt：角色定义、行为规则、可用工具列表
  • 对话历史：用户消息 + Agent回复的完整记录
  • 工具结果：每次工具调用的返回数据
  • 检索上下文：从知识库/数据库中检索的相关信息
  • 工作记忆：Agent自己维护的状态变量

管理策略

滑动窗口（Sliding Window）

最简单的策略——保留最近N条消息。超出窗口的旧消息被丢弃。优点是实现简单，缺点是可能丢失关键上下文。

摘要压缩（Summary Compression）

当上下文接近上限时，使用LLM将旧消息压缩为摘要。这样既保留了关键信息，又节省了token空间。

def compress_context(messages, max_tokens):
    """将对话历史压缩为摘要"""
    if count_tokens(messages) <= max_tokens:
        return messages

    # 保留最近的消息 + 压缩旧消息
    recent = messages[-4:]
    older = messages[:-4]

    summary_prompt = f"""
    请将以下对话历史压缩为简洁的摘要，保留关键信息：

    {format_messages(older)}

    摘要："""

    summary = llm(summary_prompt)
    return [{"role": "system", "content": f"对话摘要：{summary}"}] + recent

检索增强（RAG-based）

不在context中保留所有历史，而是在需要时从外部存储中检索相关信息。这是目前最实用的方案。

分层存储（Tiered Storage）

将信息按重要性分层：

  • 热层（Hot）：最近对话 + 当前任务状态（完整保留）
  • 温层（Warm）：近期摘要 + 用户偏好（压缩保留）
  • 冷层（Cold）：长期记忆 + 历史数据（向量数据库检索）

最佳实践

  • 优先级排序：System Prompt > 当前任务 > 工具结果 > 对话历史
  • 监控token使用：始终追踪当前context的token计数，在接近上限前主动管理
  • 结构化消息：区分消息类型（user/assistant/system/tool），便于管理
  • 工具结果截断：过长的工具输出应截断并告知模型"结果已截断"
  • 测试上下文边界：在长对话场景下测试上下文管理的效果
